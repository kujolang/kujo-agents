# KUJO Ecosystem Dossier Template

## Executive Summary

Brief factual summary of the inspected KUJO ecosystem.

Evidence status: confirmed / inferred / planned / unknown.

## One-Sentence Description

A single source-grounded sentence describing KUJO.

Evidence status: confirmed / inferred / planned / unknown.

## What KUJO Is

Describe KUJO based on inspected sources.

Include:

- Language identity.
- Runtime or interpreter facts.
- Repository evidence.
- Boundaries between language, tooling, workflows, and examples.

## Why KUJO Exists

Summarize source-supported motivations, problems, or design goals.

If motivation is not explicit, mark it unknown or inferred.

## Core Language Concepts

List source-supported language concepts, syntax, runtime behavior, or standard library concepts.

For each concept:

- Name.
- Description.
- Source note.
- Evidence status.

## Tooling Ecosystem

Map tools and their supported behavior.

For each tool:

- Tool name.
- Repository or folder.
- Purpose.
- Main commands or entrypoints.
- Inputs and outputs.
- Artifacts generated.
- Integration points.
- Evidence status.

## Workflow Ecosystem

Map workflows, workflow packs, or automation patterns.

For each workflow:

- Name.
- Location.
- Purpose.
- Inputs.
- Outputs.
- Required tools.
- Evidence status.

## Skills And Agents

Map KUJO-related skills and agent packages.

For each skill or agent:

- Name.
- Location.
- Trigger or use case.
- Required sources or tools.
- Output expectations.
- Evidence status.

## Repository Map

List inspected repositories and folders.

For each repository:

- Path.
- Apparent purpose.
- High-signal files inspected.
- Important commands or APIs.
- Open questions.
- Evidence status.

## Public Positioning

Record only source-supported positioning language.

Include:

- Phrases used by the project itself.
- Where the phrase appears.
- Whether it is current, historical, or planned.

Avoid rewriting positioning as marketing copy.

## Audience / ICP

Describe source-supported target users or use cases.

Separate:

- Explicit audience claims.
- Inferred users based on examples and workflows.
- Unknown audience gaps.

## What Is Confirmed

Bullet list of facts directly supported by inspected sources.

Each bullet must include a source note.

## What Is Inferred

Bullet list of relationships or interpretations that are plausible but not directly stated.

Each bullet must include the evidence behind the inference.

## What Is Planned

Bullet list of roadmap, TODO, proposal, or future-facing items.

Each bullet must identify the planning source.

## What Is Unknown

Bullet list of gaps, conflicts, missing sources, unclear ownership, or unverified claims.

## What To Avoid Saying

List claims that should not be made because they are unsupported, misleading, outdated, too broad, or contradicted by inspected sources.

## Glossary

Define source-supported ecosystem terms.

For each term:

- Term.
- Definition.
- Source note.
- Evidence status.

## Source Notes

Use this format:

- `[S1]` Path: `path/to/source`
  Type: README / docs / example / test / source / CLI output / metadata / script / workflow / skill / planning note.
  Detail: section, command, symbol, or line reference when available.
  Supports: short description of the supported claim.
  Evidence status: confirmed / inferred / planned / unknown.
